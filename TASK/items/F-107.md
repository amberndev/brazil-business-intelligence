# F-107 — F-102 crash creates orphaned active keys (unrecoverable + test data left live)

## F-107 | categoria: funcional | severidade: média | status: aberto
- Tela: consequence of [[F-102]] — network panel shows POST /v1/keys → 201, but UI never displays the returned key
- Passos: 1) Create a FREE key via /app/keys UI 2) UI throws and hangs on "Creating…" (F-102) 3) key is committed server-side but never shown
- Esperado: a key is shown exactly once and the user can save it; a failed/abandoned creation should not leave an unusable active key.
- Observado: because the UI crashes AFTER the backend 201 commit, the generated key value is lost forever (the endpoint intentionally returns it only once). The row stays `active=TRUE` in `product.api_keys`. The user cannot self-delete it (DELETE /v1/keys/me requires the key value). Each retry mints another orphan and consumes the per-IP creation throttle (5/hr).
- Test-data note: during this re-test, the UI creation for **qa-testdata-20260906@ambern.dev** produced exactly such an orphan (201, value lost to the F-102 crash) — it could NOT be deleted via API and is **left active in the DB**. Please deactivate it manually:
  `UPDATE product.api_keys SET active=FALSE WHERE email='qa-testdata-20260906@ambern.dev';`
  (The other test key, probe+20260906@ambern.dev, WAS created via curl and successfully revoked via DELETE /v1/keys/me → 204, verified 401 on reuse.)
- Impact: orphaned live credentials accumulate; primarily resolved by fixing [[F-102]], but consider returning key metadata / an idempotent re-issue path so a failed client render doesn't strand a key.
