# F-106 — Key validation/save on /app/keys is broken because validateApiKey() calls the failing /v1/search

## F-106 | categoria: funcional | severidade: alta | status: aberto
- Tela: HTTPS curl (GET /v1/search?limit=1 → 500) + frontend/src/lib/api.ts:86-99
- Passos: 1) On /app/keys, paste a VALID FREE key into "API Key" and click "Save Key" (or load a page with a stored key)
- Esperado: valid key → "✓ Key active" with plan + remaining; key saved to localStorage.
- Observado: `validateApiKey()` validates by calling `GET /v1/search?limit=1` (api.ts:90). That exact call returns **500** on the live server (verified: 500 after 34.6s — the no-`q` default search, see [[F-103]]). So `validateApiKey` returns `{ok:false}` for a perfectly valid key → the page shows "✗ Validation failed" / treats the key as invalid, and the auto-validate-on-load path fails the same way.
- Evidence: `curl -H "X-API-Key: <valid FREE key>" https://brazil.ambern.dev/api/v1/search?limit=1` → STATUS=500. (Could not exercise the UI Save path directly — the browser credential-entry guard blocks typing a key — but the underlying call is proven to 500.)
- Impact: even with a valid key (obtained via curl, since the UI create flow is also broken — [[F-102]]), a user cannot save/activate it in the app → the entire authenticated app (search + company pages) is unreachable through the UI. Fix by (a) fixing search [[F-103]], and/or (b) validating via a cheap endpoint such as `GET /v1/keys/me` instead of a full-table search.
